# Docs Writing

Documentation lives in three places, each with a different audience. Know which one your change belongs in.

| Location | Audience | Ships as |
|----------|----------|----------|
| `packages/sentry-testkit-docs/docs/` | Users looking things up | [zivl.github.io/sentry-testkit](https://zivl.github.io/sentry-testkit) (Docusaurus) |
| `README.md` (repo root) | Someone evaluating the package | The npm landing page |
| `AGENTS.md`, `skills/`, `CONTRIBUTING.md` | Contributors and AI agents | Repo only |

**The root `README.md` is copied into the package on `prepack`.** It is what npm renders. Treat it as a shop window: what the library is, install, minimal example, link to the docs site. Anything longer belongs on the docs site.

---

## Rule: a public API change is not done until docs change

If a change touches `types.ts` or alters observable behavior, it is incomplete without a docs update in the same PR. Docs that lag a release are worse than no docs — users trust them and get burned.

Adding a public method or type requires:

- [ ] An entry in the method list at the top of `docs/api/README.md`
- [ ] A `### methodName()` reference section with Returns, a description, and a runnable example
- [ ] The `Report` / `Transaction` / `Log` type documented if the shape is new
- [ ] A migration note under `docs/migration/` if anything is breaking

## Docusaurus conventions

Every doc page starts with frontmatter. Missing it produces a page with a filename for a title.

```markdown
---
title: Getting Started
description: Getting started with Sentry Testkit
sidebar_position: 1
---

# Getting Started
```

- **`title`** — sidebar and browser tab text.
- **`description`** — used for SEO and search results. Write a real sentence, not a keyword list.
- **`sidebar_position`** — ordering within the section. The sidebar is autogenerated from the filesystem, so this number is the only ordering control. Check neighboring files before picking one.

Directory ordering and labels come from `_category_.json`:

```json
{ "label": "Migration", "position": 5 }
```

Preview locally before pushing — broken MDX fails the docs build, not just the render:

```bash
yarn workspace sentry-testkit-docs start
```

## Every API entry needs a runnable example

The single most common docs failure is describing a method without showing it in a test. Users arrive by search, land mid-page, and copy the first code block they see. Make that block work.

**Good** — complete, copy-pasteable, shows the async handling:

````markdown
### `waitForLogs(count, options)`
Waits until at least `count` logs have been captured, then resolves with them.
Rejects with a descriptive error if the timeout elapses first.

**Returns**: <code>Promise&lt;Array&lt;Log&gt;&gt;</code>

```javascript
test('captures a log', async function() {
  Sentry.logger.info('user logged in')

  const logs = await testkit.waitForLogs(1)
  expect(logs[0].message).toBe('user logged in')
})
```
````

**Bad** — no example, no return type, and a fragment that will not run:

````markdown
### `waitForLogs`
Waits for logs.

```javascript
testkit.waitForLogs(1)
```
````

Example conventions on the docs site:

- **JavaScript, not TypeScript**, in user-facing examples. Most consumers write plain JS test files, and the docs should not imply TS is required.
- **Show the assertion**, not just the call. The library's purpose is assertions.
- **Realistic scenario names.** `'user logged in'` beats `'foo'`.
- **`async`/`await`** wherever capture is asynchronous — a synchronous example teaches users to write flaky tests.

## Writing style

- **Second person, present tense.** "You get an array of reports", not "The user will be returned an array."
- **Lead with the answer.** Users are looking something up, not reading a narrative.
- **Link, do not duplicate.** One canonical explanation, referenced from elsewhere. Duplicated docs drift.
- **Name versions explicitly.** "Sentry SDK v10", not "the latest version" — which is wrong within a month.
- **Never use emojis.**

Docusaurus admonitions for genuine caveats only, not emphasis:

```markdown
:::note Raven-Testkit
The legacy `raven-testkit` documentation can be found [here](/docs/raven-testkit-legacy).
:::
```

## Do not hand-edit generated files

- **`packages/sentry-testkit/CHANGELOG.md`** is generated by release-please from conventional commits. The docs site's `changelog.md` merely links to it. Never edit either by hand — your edit will be overwritten, and the release notes come from your commit message instead. Write the commit message well; that is the changelog entry.
- **`packages/sentry-testkit-docs/build/`** is build output. Never commit edits to it.

---

## Keeping contributor docs in sync

`AGENTS.md` is the canonical instructions file; `CLAUDE.md` and `.cursorrules` point at it. When you change a convention, update `AGENTS.md` or the relevant file in `skills/` — not the pointers.

`CONTRIBUTING.md` takes precedence on commit conventions, git workflow, and releases. If `AGENTS.md` and `CONTRIBUTING.md` disagree, `CONTRIBUTING.md` wins and `AGENTS.md` should be corrected.

## Checklist

- [ ] Public API change reflected in `docs/api/README.md` (both the list and the reference section)
- [ ] New pages have `title`, `description`, `sidebar_position`
- [ ] Every documented method has a runnable example with an assertion
- [ ] Async examples use `await`
- [ ] Root `README.md` updated only if the elevator pitch or install steps changed
- [ ] Migration page added for breaking changes
- [ ] No hand edits to `CHANGELOG.md` or `build/`
- [ ] Docs site builds locally
- [ ] No emojis
